# Changelog

## Unreleased

- **The server has an icon** (#61): the tg-mcp mark (`site/favicon.svg`, never Telegram's logo). It is served at `/icon.svg`, `/icon.png` (128×128), `/icon-256.png`, `/icon-512.png` and `/favicon.ico` (a 32×32 PNG), unauthenticated and cached for a day. `serverInfo` advertises `icons` (PNG 128, PNG 256, SVG, as absolute URLs on the public host) and `websiteUrl`. The sign-in pages link it as their favicon, with their CSP unchanged. The PNGs are pre-rendered from the SVG and committed (`assets/icon/`, see its README).
- **No confirmation page: `send_message` sends at once** (#72, [ADR-0008](docs/adr/0008-writes-are-approved-by-the-client.md)). Whether you approve each message is now your AI app's business (its permission prompts); the server still enforces the Send allow-list (only chats you already have), the writes budget, the per-chat Send cap (5 a minute), the duplicate guard and never forwarding. **Connections made before this that had confirmation on now send at once, without asking you on a page**: if you don't want that, remove the connector, or connect again without "Send messages". `send_message` returns `status: "sent"` with `message_id` and `date`, or an error: `pending_confirmation`, `confirm_url`, `expires_at`, `cancelled`, `drafted` and `expired` are gone. It is annotated destructive and open-world (`react` and `mark_read` open-world), so clients ask before calling it by default; nothing on the server relies on that.
- Removed with it: `/confirm/{id}` (now 404) and its rate limit (`TG_MCP_CONFIRM_PER_MINUTE` / `TG_MCP_CONFIRM_BURST` are ignored), pending sends, URL elicitation, the `tgm_confirm_…` cookie (no longer set or read; one left in a browser expires on its own) and the Consent screen's "Send to these chats without asking me" switch. The server's instructions and the tool descriptions no longer mention confirming. Send allow-lists sealed before still open; their Auto-send flag and cookie verifier are ignored.
- **Landing page: text apart from behaviour.** The page's script moved to `site/landing.js`, shared by every language page; the text it shows (install steps and notes, the phone demo's messages and tool-call details, Copy / Copied, the star count's label) comes from a dictionary picked by `<html lang>`, and any key a language leaves out, or gives in the wrong shape, falls back to English. The English page looks and works as before. `tests/site/landing-check.cjs` checks the page with Playwright (widths, requests, the buttons, the demo, the fallback, no JavaScript).

### Changed

- **A tool called with a parameter it doesn't take is an error** (#60), not a silent default: `invalid_params` `` unknown parameter `pinnedOnly`; did you mean `pinned_only`? `` when a known parameter is close (the same letters whatever the case and `_`, or a couple of edits away), else `` unknown parameter `foo`; this tool takes: … ``. Every tool's input schema says `additionalProperties: false`, so clients that validate locally catch it first. One check for all tools, before the tool runs: new tools get it too.

### Fixed

- **`list_chats` no longer drops pinned chats beyond `limit`** (#68). With more pinned chats than `limit`, the next page goes on with the next pinned chat instead of starting the unpinned list, so every pinned chat appears once across the pages of one listing: main list, Archive and `unread_only` alike. A page that continues the pinned chats is still one `messages.getDialogs` call. Cursors issued before keep working as they did.

## 0.2.0

### New address

- **The public instance moved to `https://connector.tgmcp.dev/mcp`.** `https://tgmcp.qelphybox.space/mcp` stops answering: remove the connector and add it again with the new URL (claude.ai: Settings → Connectors; Claude Code: `claude mcp remove telegram`, then `claude mcp add --transport http telegram https://connector.tgmcp.dev/mcp`). You sign in again with the QR code; then end the old **Unofficial MCP Server** session in Telegram → Settings → Devices.
- A landing page at [tgmcp.dev](https://tgmcp.dev), published from `site/` with GitHub Pages.

### Sign-in pages in the landing page's look

- Login, cloud password, Consent, the send confirmation and every error page share the landing page's wallpaper, glass card and type (Unbounded, Golos Text). Dark only.
- **The login QR code is drawn by the server**: round dots, rounded finder patterns, the tg-mcp mark in the middle, error correction H (was M) so the covered centre still scans. While it is prepared, a loader in the same grid; the code settles in with a diagonal reveal.
- **The Consent screen has two columns on a wide screen**: who asks and what it may do on the left, the chats it may send to on the right, Deny / Allow in a bar under both (one column with that bar pinned to the bottom on a phone). Write Scopes and "without asking me" are switches; with sending off, the right column says so and offers to turn it on. Same form fields and the same text as before.
- The fonts (SIL Open Font License, licences in `assets/fonts/`) and the wallpaper pattern are served from `/login/assets/`. The pages load nothing from anywhere else: the confirmation page's CSP now allows images and fonts from `'self'`, the Login flow's fonts from `'self'`.

### New

- **Drafts, the first write.** `save_draft` (Scope `draft`) puts text into a chat's message field on all the account's devices, replacing the Draft there; `""` clears it, and nothing is ever sent: the user sends it from Telegram. Text is a small Markdown subset by default (bold, italic, inline code, code blocks, links; anything else stays as typed) or `format: "plain"`, at most 4096 characters once formatted (longer is an error, never split). `reply_to` replies to a message of the chat; in a forum, `topic` (or a `reply_to` in a Topic) names the Topic, and neither is an error. Any chat of the account's, no allow-list. Each call spends the writes budget; the text is never logged, only ids and sizes. Annotated not read-only, not destructive, idempotent.
- `get_drafts` (Scope `read`): the account's Drafts, newest first, with chat, forum Topic, `reply_to`, date and text (sanitised like message text); at most 100 and ~40,000 characters per call.
- MCP clients keep the tool list they fetched when the connector was added: reconnect it (claude.ai: Settings → Connectors; Claude Code: a new session) to see `get_drafts`, and connect again with "Write Drafts" ticked to get `save_draft`.
- **Scopes.** Each connection (Grant) has Scopes, chosen on the consent screen: `read`, always, and `draft` (writing Drafts with `save_draft`). `send` and `organize` are listed in `scopes_supported` of both OAuth metadata documents but not offered yet: asking for them grants nothing more. `/authorize` takes `scope` (space-separated; an unknown one is `invalid_scope`), and the boxes it asks for start ticked; the token response's `scope` says what was granted, and a refresh keeps it whatever it asks for. Other Scopes mean connecting again.
- `tools/list` lists only the tools a connection's Scopes allow; calling another one is an error that names the missing Scope. The server's `instructions` and the consent screen say "read-only" only while no write Scope is granted.
- Connections made before Scopes become `read` and keep working: no re-login.
- MCP clients that ask for every advertised Scope (the MCP spec's default when the 401 names none) open the consent screen with "Write Drafts" ticked; untick it to stay read-only.
- **`send` is offered on the consent screen, with its Send allow-list.** Ticking "Send messages" and pressing "Choose chats" lists the account's Chat folders that are explicit lists (rule-based ones are left out), its 100 most recent chats, and a search by name that shows only the account's own chats with an existing dialog (never a contact it never wrote to, nor a public chat it isn't in). A ticked folder is read into its chats when you allow. Allow with "Send messages" ticked and no chat chosen is refused and the page says why. "Send to these chats without asking me each time" is off unless ticked. "Send messages" never starts ticked, even when the client asks for `send`. Changing the chats means connecting again.
- **`send_message`** (Scope `send`, absent from `tools/list` without it): sends a message as the user, only to a chat of the connection's Send allow-list (any other is an error naming the list). Text as `save_draft`'s: the Markdown subset by default or `format: "plain"`, 1 to 4096 characters once formatted, never split; `reply_to` a message of the same chat (no partial quotes); in a forum `topic`, or a `reply_to` in a Topic, and neither is an error. Text only: no media, never forwarding. Unless the connection has auto-send, each message waits for you on the confirmation page (below). Returns `sent` (`message_id`, `date`), `cancelled`, `expired`, `drafted` (you made it a Draft) or `pending_confirmation` (`confirm_url`, `expires_at`). Each message spends the writes budget and the chat's Send cap. Annotated not read-only, not idempotent, closed-world.
- **`react`** (Scope `send`): sets the account's reaction on one message of a chat of the Send allow-list (any other chat is an error) to one standard emoji, replacing its previous reaction there; `emoji: null` removes it (`emoji` must be given). The emoji is matched against Telegram's own list of standard reactions (`messages.getAvailableReactions`, fetched by the first `react` of a connection and kept while it is live), ignoring variation selectors (`❤️` is Telegram's `❤`), and returned as Telegram names it; anything else is an error listing them. Custom emoji (`custom`, or a custom emoji's id) and paid reactions (`paid`) are refused before Telegram is asked. A chat whose admins allow only some reactions, or none, refuses the others with an error that says so (`REACTION_INVALID`); a message the chat doesn't have, a message with as many different reactions as Telegram allows, a reaction that needs Premium and a chat the account can't react in each get their own error. Setting the reaction that is already there (`MESSAGE_NOT_MODIFIED`) is no error. Returns `set` (with the emoji) or `removed`. Annotated not read-only, idempotent, not destructive, closed-world.
- **`mark_read`** (Scope `send`): marks a chat of the Send allow-list as read up to its latest message, or up to `up_to` (`messages.readHistory`, or `channels.readHistory` for supergroups and channels); in a forum, `topic` marks only that Topic (`messages.readDiscussion`, up to the Topic's latest message unless `up_to` says otherwise), and `topic` on a chat that is no forum, or a Topic it doesn't have, is an error. The unread counter clears on all the account's devices; in a private chat the other person sees their messages as read. Returns the chat, `topic` and `up_to`. Annotated not read-only, idempotent, not destructive, closed-world.
- `react` and `mark_read` are never confirmed (ADR-0005) and need no confirmation page. Each spends the writes budget, not the chat's Send cap; a `FLOOD_WAIT` of writes, `PEER_FLOOD` or a used-up budget fails at once, saying when to retry, and nothing is retried or queued.
- **The same text to the same chat within 60 seconds of sending it is not sent again**: `send_message` answers "already sent: message N" instead. "The same text" is the message as the chat shows it (text and formatting once the Markdown is read), counted per Telegram account across its connections, and whether it was sent at once or confirmed on the page. Only a keyed hash of it is kept, in memory, for that minute.
- A `send` connection is told in the server's `instructions` that it can send messages, react to messages and mark chats as read in the chats you allowed, each message confirmed by you unless you chose otherwise, reactions and marking as read never.
- **The confirmation page for sends** (used by `send_message`). A message to a chat of the Send allow-list, from a connection without auto-send, waits up to 10 minutes on `/confirm/<id>`: the page shows the chat (and forum Topic), the text formatted as it will look with every link's target written out, the message it replies to, and who asks (where the app's login went, large; the name it gave itself, small and unverified). **Send** and **Cancel** work only in the browser that gave Consent; any other browser, a phone say, gets only **Make it a Draft**, which puts the text in the chat's message field for you to send. Decided once; an expired, decided or unknown link says "no longer valid". MCP clients that support URL elicitation (Claude Code) open the page themselves and the tool call waits for your decision (`sent` with the message id, `cancelled`, `drafted`, or `expired`); others get `pending_confirmation` with the link to give you. A connection with auto-send sends to its chats at once.

### Security

- **The Send allow-list is sealed with the Session key.** A `send` Grant's chats and its auto-send choice are one blob encrypted like its Telegram session (its own AAD, `tg-mcp/send-allow-list/v1:` + Grant id; plaintext padded to 512 bytes): a database dump without a Token shows neither the chats nor, beyond a rough size, how many; a database writer can't turn confirmation off or move a list to another Grant. Logs carry counts (`send_chats`, `auto_send`), never chat ids, titles or search terms.
- **Only the browser that gave Consent can send.** Allowing `send` sets a Confirmation cookie there (`tgm_confirm_…`: random, HttpOnly, Secure, SameSite=Strict, sent only to `/confirm`, as long-lived as a refresh Token and renewed whenever the page is opened with it). The server keeps only its SHA-256 verifier, sealed with the Send allow-list (format version 2), so a database dump holds no cookie and a database writer can't plant one; a refresh keeps it, a new connection gets a new one. The page's id (256 random bits) is a credential for Drafts only: the AI's own shell, which may see the link, can't send with it. The page runs no script (CSP `default-src 'none'`, no framing, forms only to itself), posts with a CSRF token, is rate-limited per client IP, and is never readable cross-origin. Pending sends live in memory only (a restart drops them), keep the `random_id` they will be sent with (a second press after Telegram didn't answer can't send twice), end with their connection, and are logged with ids and sizes only: never the page's id, the text or the cookie.
- A confirmed send still spends the writes budget and the chat's Send cap when it goes to Telegram; refused there (or by `FLOOD_WAIT` / `PEER_FLOOD`), it is not sent, not queued, and both the page and the tool say when to try again.
- Telegram's slow mode (`SLOWMODE_WAIT_X`) is reported as "This group is in slow mode …; retry in N s", not as a failed request: nothing was sent, it is never retried, and it holds up no other chat. A confirmed send it refuses is decided as not sent, saying when to ask again (before, it stayed pending as if Telegram hadn't answered).
- `send_message` logs its grant, chat and message ids only, never the text; a send refused as a duplicate is logged with the earlier message's id. `react` logs the grant, chat and message ids and whether a reaction was set or removed, never the emoji; `mark_read` the grant, chat, Topic and `up_to`.
- The consent screen's chat pickers reach Telegram before any Token exists: they need the login's cookie and a finished Telegram login, go through the account's own request budget, and are rate-limited per client IP (new settings below) and to 30 searches per login.
- **A reused refresh Token revokes its Grant.** A refresh Token keeps working for 60 seconds after its first use (two client processes refreshing at once, or a retry after a lost response, both get a working pair). Presented after that, or by a client it wasn't issued to, it revokes the whole Grant: every Token stops working (`/mcp` → 401) and, if the server holds a Live client for it, its Telegram session is logged out. The client sees the usual `invalid_grant`; the server logs `refresh_reuse` or `foreign_client` with the Grant id, never a Token. A wrong secret for a used Token revokes nothing.
- A used refresh Token's Wrapped key is deleted from the database within a few minutes; SQLite's `secure_delete` is on, so deleted keys leave the file.

### Operations

- Migration `0003_consumed_refresh_tokens` rebuilds the `tokens` table. An image built before it does not start on a database that ran it, so `kamal rollback` past this release fails: fix forward instead.
- Migration `0004_grant_scopes` adds `grants.scopes` (plaintext, `read` for every existing Grant). Same rollback rule.
- Migration `0005_send_allow_list` adds `grants.send_allow_list` (a sealed blob, NULL for every existing Grant and for Grants without `send`). Same rollback rule.
- New settings: `TG_MCP_CONSENT_CHATS_PER_MINUTE` (default 20), `TG_MCP_CONSENT_CHATS_BURST` (default 10), the per-IP rate limit of the consent screen's chat pickers (`/login/{id}/consent/chats`).
- New settings: `TG_MCP_CONFIRM_PER_MINUTE` (default 30), `TG_MCP_CONFIRM_BURST` (default 10), the per-IP rate limit of the confirmation page (`GET` and `POST /confirm/{id}`, one bucket).
- The Send allow-list blob is now format version 2 (with the Confirmation cookie's verifier); no migration. Lists sealed as version 1 still open, without a cookie: their pending sends can only be made Drafts. A rollback to an image without #45 can't open version-2 lists: those connections then fail to open (connect again).
- New settings for the write tools: `TG_MCP_ACCOUNT_WRITES_PER_10_MIN` (default 20), the Writes budget, writes per account in any 10 minutes on top of the request budget (`save_draft` is the first write to spend it); `TG_MCP_CHAT_SENDS_PER_MINUTE` (default 5), the Send cap, messages sent to one chat in any minute. A write over either, or in a `FLOOD_WAIT` of writes, fails at once with "retry in N s": writes never wait inside a call, are never retried and never queued. Telegram's `PEER_FLOOD` (the account is limited for spam) is reported as such, never retried. Reading is unaffected.

## 0.1.3

### Breaking: message media is a field of its own

- `get_messages` messages carry `media` as an object: `{ kind, duration_s?, size_bytes?, mime_type?, file_name?, width?, height? }`. `list_chats` previews and `search_messages` hits carry `{ kind }`.
- `text` is only a message's text or caption, possibly empty. The old placeholders (`[photo]`, `[voice]`, `[file]`, …) are gone.
- **Reconnect the connector after upgrading.** MCP clients (claude.ai, Claude Code, others) keep the tool list they fetched when the connector was added. Until it is reconnected (claude.ai: Settings → Connectors; Claude Code: a new session), a client checks answers against the old schemas: `search_messages` fails output validation on hits with media, and new tools, modes and parameters (`get_media` `view` / `transcribe`, `get_members`, `pinned_only`, `topic`) are unknown to the model.

### New

- **`get_media`**, one tool for a message's media, in three modes:
  - `download`: a Media link, a short-lived URL (5 minutes, 3 downloads, in memory only) that an agent with a shell fetches with curl. Files up to 20 MB, streamed from Telegram, never written to disk.
  - `view`: the picture itself as image content, for clients without a shell (claude.ai web, desktop and mobile). Photos, thumbnails of videos, video messages, GIFs and stickers; whole albums up to 4 images; about 1 MB per call.
  - `transcribe`: what a voice message or video message says, transcribed by Telegram itself (`messages.transcribeAudio`); the audio never leaves Telegram. Needs Telegram Premium or Telegram's free weekly transcriptions.
- **`get_members`**: a group's members and admins, with roles; says when Telegram hides them.
- **`get_chat_info` on a user**: bio, phone and birthday as Telegram shows them to the account, last-seen status, and common chats on request.
- **Forum Topics**: `get_chat_info` lists a forum's Topics, each message says its Topic, and `get_messages` / `search_messages` read one Topic.
- **Reactions, links and pins** on messages: `reactions` counts, a `t.me` `link` for channel and supergroup messages, `pinned`; `get_messages` `pinned_only` reads only the pinned messages.

### Fixed

- A sender id at the newest edge of a chat comes with its access hash, so it works as a chat id at once.
- The account's own messages in Saved Messages are outgoing, not from a sender; forwards there show the original author.
- A window read at a chat's newest message reads the top again instead of coming back short.

### Operations

- kamal-proxy no longer buffers responses (`proxy.buffering.responses: false`), so media files are passed through, not spooled to its disk.
- New settings: `TG_MCP_MEDIA_PER_MINUTE`, `TG_MCP_MEDIA_BURST` (per-IP rate limit of `/media/…`).
