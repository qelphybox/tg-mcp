# Telegram facts for each kind of action ADR-0005 rules out

**Question.** ADR-0005 puts these categories out of scope: group administration, joining and leaving Chats, forwarding, bot inline buttons, contacts, and profile and privacy. The project now considers offering some of them. For each kind of action in those categories, at TL layer 230 as pinned by `grammers-tl-types =0.11.0`, this note records:

- which TL methods the action takes;
- whether it can be undone, and how;
- whose data it exposes, and to whom;
- what limits and anti-spam consequences Telegram applies;
- which admin rights it needs in the Chat.

The note also lists the account-level methods (sessions, Cloud password, phone number, account deletion, URL authorization, Takeout and anything else that hands over the Account or locks the user out), so that a never-list can be complete.

**Ticket:** [qelphybox/tg-mcp#83](https://github.com/qelphybox/tg-mcp/issues/83). This is research, not a design recommendation. Researched on 2026-11-14.

**Sources and their trust.**

- **Schema** (authoritative for method names, flags and parameters at layer 230): `/root/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/grammers-tl-types-0.11.0/tl/api.tl`, cited as `api.tl:LINE`. The file starts with `// LAYER 230`.
- **core.telegram.org** method, constructor and guide pages, linked inline. **These pages document layer 225**, not 230 (every method page shows "Layer 225"). Where the two differ, the schema wins, and the note says where the site has no page for a layer-230 method (see §0).
- **telegram.org** [Spam FAQ](https://telegram.org/faq_spam) and [FAQ](https://telegram.org/faq).
- **Bot API** docs ([core.telegram.org/bots/api](https://core.telegram.org/bots/api), [/bots/webapps](https://core.telegram.org/bots/webapps)). These describe what the *bot* side receives. They are first-party but describe the HTTP Bot API, not MTProto.
- One secondary source, used only to name an error that the primary docs never list: Telethon's error table ([errors.csv](https://sources.debian.org/data/main/p/python-telethon/1.42.0-1/telethon_generator/data/errors.csv)). It is marked **(secondary)** wherever it is used.

**Conventions.** Every claim from a source carries its link or `api.tl` line. **(analysis)** marks this note's own reasoning about tg-mcp. **(inference)** marks a conclusion drawn from documented facts that no source states outright. **(unverified)** marks a fact this note could not check against a primary source. Anti-spam thresholds are almost entirely undocumented, so this note gives no numbers for them unless Telegram publishes one.

## 0. Cross-cutting facts

### 0.1 Layer 230 differs from the documented layer 225

- **Buttons are restructured.** At layer 230 a reply-keyboard button is `keyboardButton … text:string type:ButtonType` (`api.tl:722`). Its type is `buttonTypeDefault`, `buttonTypeRequestPhone`, `buttonTypeRequestGeoLocation`, `buttonTypeRequestPoll`, `buttonTypeRequestPeer` or `buttonTypeSimpleWebView` (`api.tl:2252-2258`). An inline button is `keyboardInlineButton … type:InlineButtonType` (`api.tl:2273`), with the types `inlineButtonTypeUrl`, `…UrlAuth`, `…WebView`, `…Callback` (with `requires_password`), `…Game`, `…Buy`, `…SwitchInline`, `…UserProfile`, `…Copy` and `…Disabled` (`api.tl:2260-2271`). The site still documents the layer-225 constructors (`keyboardButtonCallback`, `keyboardButtonUrlAuth`, …). This note uses the site's text for what each kind does and the schema for the shape.
- **Ownership transfer** is `messages.editChatCreator peer user_id password` (`api.tl:2807`) and covers basic groups, supergroups and channels ([method page](https://core.telegram.org/method/messages.editChatCreator)). The site's `channels.editCreator` is not in the layer-230 schema.
- **New at 230, with no page on the site:** `wallet.*` (a TON wallet: `wallet.exportSecretPhrase`, `wallet.sendTransfer`, `wallet.replaceWallet`, `wallet.disableBackup`, `wallet.tonConnect*`, `api.tl:3211-3235`) and `messages.requestChatJoinWebView` (`api.tl:2826`). Also new: join results that send the user to a guard bot first. `messages.importChatInvite` and `channels.joinChannel` return `messages.ChatInviteJoinResult`, which is either `chatInviteJoinResultOk` or `chatInviteJoinResultWebView bot_id query_id` (`api.tl:2216-2217`). Admins can set that up with `channels.toggleJoinRequest … guard_bot:flags.0?InputUser` (`api.tl:2910`). The pages for `wallet.exportSecretPhrase`, `wallet.sendTransfer` and `messages.requestChatJoinWebView` are empty on the site as fetched.
- `bots.createBot` (`api.tl:2963`) lets a *user* create a managed bot owned by them and controlled by a manager bot ([method page](https://core.telegram.org/method/bots.createBot); limit `bots_create_limit_default` 20 / premium 40 in the [client config](https://core.telegram.org/api/config)).

### 0.2 Error classes that matter for every write

- **420 FLOOD:** `FLOOD_WAIT_X` and `FLOOD_PREMIUM_WAIT_X` mean "The maximum allowed number of attempts to invoke the given method with the given input parameters has been exceeded" ([errors](https://core.telegram.org/api/errors)).
- **Other 420 names that are not account floods** appear on method pages: `SLOWMODE_WAIT_%d` (per Chat; [forwardMessages](https://core.telegram.org/method/messages.forwardMessages)), `FROZEN_METHOD_INVALID` ("The current account is frozen, and thus cannot execute the specified action", [channels.joinChannel](https://core.telegram.org/method/channels.joinChannel)), `2FA_CONFIRM_WAIT_%d` ([account.deleteAccount](https://core.telegram.org/method/account.deleteAccount)) and `TAKEOUT_INIT_DELAY_%d` ([account.initTakeoutSession](https://core.telegram.org/method/account.initTakeoutSession)). **(analysis)** `flood_seconds` in `src/tg/grammers.rs` keys on code 420 *and* a name starting with `FLOOD_`, so these other 420 errors already fall through to "upstream". That is correct for `FROZEN_METHOD_INVALID`, which is a refusal, not a wait.
- **Frozen accounts.** The client config carries `freeze_since_date`, `freeze_until_date` ("when a frozen account be deleted, unless an appeal is submitted to the freeze_appeal_url and accepted") and `freeze_appeal_url` ([config](https://core.telegram.org/api/config)). No guide page for frozen accounts exists (`/api/frozen-accounts` returns "Page not found"). What triggers a freeze is undocumented.
- **`USER_RESTRICTED`** (406 or 403): "You're spamreported, you can't create channels or chats" ([channels.createChannel](https://core.telegram.org/method/channels.createChannel), [messages.createChat](https://core.telegram.org/method/messages.createChat), [channels.editAdmin](https://core.telegram.org/method/channels.editAdmin)).
- **`PEER_FLOOD`** appears on no core.telegram.org page fetched for this note, including `messages.sendMessage`, `messages.forwardMessages`, `channels.inviteToChannel` and `contacts.importContacts`. Telethon's table lists it as `PEER_FLOOD,400,Too many requests` **(secondary)**. Telegram's own [Spam FAQ](https://telegram.org/faq_spam) describes the state it most likely corresponds to **(inference)**. A reported account "becomes limited temporarily"; "Limited accounts can send messages to people who have their number saved as a contact. You can also always reply to anyone who messages you first"; "Repeated offences will result in longer periods of being blocked … you may lose the ability to do so forever". The FAQ names the triggers as unsolicited messages to strangers and "adding people to unwanted groups and channels". The only remedy it gives is to wait, or @SpamBot if the limit was wrong.
- **Fresh-session guards:** Telegram refuses some powerful actions from a session that is less than 24 hours old: `FRESH_RESET_AUTHORISATION_FORBIDDEN` ([auth.resetAuthorizations](https://core.telegram.org/method/auth.resetAuthorizations)), `FRESH_CHANGE_PHONE_FORBIDDEN` ([account.sendChangePhoneCode](https://core.telegram.org/method/account.sendChangePhoneCode)), `FRESH_CHANGE_ADMINS_FORBIDDEN` ("You were just elected admin, you can't add or modify other admins yet", [channels.editAdmin](https://core.telegram.org/method/channels.editAdmin)) and `SESSION_TOO_FRESH_%d` ([messages.editChatCreator](https://core.telegram.org/method/messages.editChatCreator)). **(analysis)** These guards protect the user only during the first 24 hours of a Grant's Telegram session. After that, tg-mcp's session can do everything an old phone session can.

### 0.3 Limits Telegram does publish (client config defaults)

These come from the defaults in the [client configuration](https://core.telegram.org/api/config), which clients must use when a key is missing. The server may send other values.

| Key | Default / Premium | Meaning |
|---|---|---|
| `channels_limit_*` | 500 / 1000 | "maximum number of channels and supergroups a … user may join" (`CHANNELS_TOO_MUCH`) |
| `channels_public_limit_*` | 10 / 20 | public channels/supergroups one may admin (`CHANNELS_ADMIN_PUBLIC_TOO_MUCH`) |
| `chatlists_joined_limit_*` | 2 / 20 | shared Chat folders one may join |
| `chatlist_invites_limit_*` | 3 / 100 | folder links one may create |
| `about_length_limit_*` | 70 / 140 | bio length |
| `bots_create_limit_*` | 20 / 40 | managed bots one may own |
| `authorization_autoconfirm_period` | 604800 (7 days) | an unconfirmed new session is auto-confirmed after this |
| `config.forwarded_count_max` | (server value) | "Maximum number of messages that can be forwarded at once" ([config](https://core.telegram.org/constructor/config)) |
| `config.revoke_time_limit`, `revoke_pm_time_limit` | (server value) | only messages younger than this can be deleted for everyone ([config](https://core.telegram.org/constructor/config)) |

**Not published anywhere fetched:** how many joins, leaves, invites, contact imports, forwards or button presses per hour or per day an account may make before FLOOD_WAIT, PEER_FLOOD, a spam limit or a freeze. The only rate Telegram states for any method in these categories is client-side debouncing of `contacts.resolvePhone`: "at most 1 call every 3 seconds" ([contacts.resolvePhone](https://core.telegram.org/method/contacts.resolvePhone)). For login attempts, it says "Each phone number is limited to only a certain number of login attempts per day (e.g. 5, but this is subject to change)" ([auth](https://core.telegram.org/api/auth)).

## 1. Group administration

The rights named are `chatAdminRights` flags (`api.tl:1293`; [constructor](https://core.telegram.org/constructor/chatAdminRights)). Two caveats about them:

- **(inference)** core.telegram.org does not map methods to rights. The [rights guide](https://core.telegram.org/api/rights) only lists the flags, and method pages only say `CHAT_ADMIN_REQUIRED` or `RIGHT_FORBIDDEN`. So the "rights" column pairs each method with the flag whose description matches it.
- Basic groups have no granular rights: "Basic groups cannot set granular admin rights or restrict individual users with channels.editBanned", and members are removed with `messages.deleteChatUser` ([rights](https://core.telegram.org/api/rights)).

## 2. Joining and leaving Chats

| Kind of action | TL methods | Undo | Data exposed, to whom | Limits / anti-spam | Rights |
|---|---|---|---|---|---|
| Look at an invite link before joining | [`messages.checkChatInvite`](https://core.telegram.org/method/messages.checkChatInvite) `hash` | read-only | Returns `chatInvite` (title, about, participant count, some participants), `chatInviteAlready`, or `chatInvitePeek`, which allows reading "until the time in the `expires` field" ([invites](https://core.telegram.org/api/invites), [chatInvitePeek](https://core.telegram.org/constructor/chatInvitePeek)). | Join by private invite link | [`messages.importChatInvite`](https://core.telegram.org/method/messages.importChatInvite) `hash` (`api.tl:2607`) | Leave. Joining through one transfers Stars ([invites](https://core.telegram.org/api/invites)). `CHANNELS_TOO_MUCH`, `USERS_TOO_MUCH`. | none |
| Join a shared Chat folder | [`chatlists.checkChatlistInvite`](https://core.telegram.org/method/chatlists.checkChatlistInvite) → [`chatlists.joinChatlistInvite`](https://core.telegram.org/method/chatlists.joinChatlistInvite) `slug peers` (`api.tl:3124`), `chatlists.joinChatlistUpdates` | [`chatlists.leaveChatlist`](https://core.telegram.org/method/chatlists.leaveChatlist) `peers` ("Also leave the specified channels and groups") | **Joins several Chats in one call** (the `peers` list) and adds a Chat folder. Each join is a normal join (`via_chatlist` in the admin log, `api.tl:1101`). | `chatlists_joined_limit_default` 2, `CHANNELS_TOO_MUCH` | none |
| Leave a supergroup or channel | [`channels.leaveChannel`](https://core.telegram.org/method/channels.leaveChannel) | Rejoin only if the Chat is public or a valid link exists. A private Chat with no link is lost. | Admin log `ParticipantLeave` (`api.tl:1085`) | `USER_CREATOR` (older layers), `CHANNEL_PRIVATE` | none |
| Leave a basic group | [`messages.deleteChatUser`](https://core.telegram.org/method/messages.deleteChatUser) `chat_id user_id=inputUserSelf` ([channels](https://core.telegram.org/api/channel)) | as above | `messageActionChatDeleteUser` visible to members | n/a | none |
| Leave as the owner | [`messages.getFutureChatCreatorAfterLeave`](https://core.telegram.org/method/messages.getFutureChatCreatorAfterLeave) then leave ([channels](https://core.telegram.org/api/channel)) | Rejoin within 7 days. Otherwise "ownership will be transferred to the new admin", **irreversibly**. | Members see `messageActionNewCreatorPending`, then `messageActionChangeCreator` (`api.tl:209-210`) | none documented | owner |
| Start a bot in a group (adds the bot) | [`messages.startBot`](https://core.telegram.org/method/messages.startBot) `bot peer start_param` | Remove the bot | The bot joins the group and can see what its privacy mode allows **(inference)** | `CHAT_ADMIN_REQUIRED` | admin / `invite_users` |

**(analysis)** Joining is the action with the most hidden cost:

- **Visibility.** The Account becomes visible to strangers: members, admins, guard bots.
- **Money.** It can spend Stars.
- **Batching.** One folder link joins many Chats at once.
- **Hard cap.** The 500-Chat limit is a hard wall.
- **Abuse limits are undocumented.**

Leaving is cheap to do and often impossible to undo for private Chats. For an owner, leaving is a delayed ownership transfer.

## 3. Forwarding

| Kind of action | TL methods | Undo | Data exposed, to whom | Limits / anti-spam | Rights |

| Forward to Saved Messages | `messages.forwardMessages to_peer=inputPeerSelf` | delete | stays within the Account **(inference)** | as above | none |
| Forward a login code | any forward of a text message from user 777000 | n/a | "Telegram's servers will automatically invalidate login codes if they are sent by the user to another Telegram chat, either by forwarding them or by sending them inside of a message", and clients should call `account.invalidateSignInCodes` ([auth](https://core.telegram.org/api/auth)) | n/a | n/a |

**(analysis)** At the Telegram level, forwarding is send plus a pointer to the source:

- **It moves other people's words.** The content is someone else's. That is the exfiltration channel ADR-0005 worried about.
- **The source is attributed.** The header can name a third party, and the third party's own privacy setting decides whether it does.
- **Undo is only partial.** Deletion is bounded by the revoke time limits, and it cannot reach copies already seen.
- **Some flags spend or repeat.** `allow_paid_stars` spends money, and `schedule_repeat_period` turns one call into repeated sends.

- **Web App** hands over the profile and lets the bot send as the user.
- **`requires_password` callback** proves the Cloud password.

## Open uncertainties

1. **Anti-spam thresholds are undocumented.** No primary source gives rates or counts for joins, leaves, invites, contact imports, forwards or button presses before `FLOOD_WAIT`, `PEER_FLOOD`, a spam limit or a freeze. The published numbers are hard caps (500 joined Chats, 10 public Chats, 2 joined folders) and one client-side debounce (`contacts.resolvePhone`, 1 per 3 s).
2. **`PEER_FLOOD` is undocumented by Telegram.** Its meaning here (the Account is spam-limited: it can write only to mutual contacts and to people who wrote first) comes from Telethon **(secondary)** plus the Spam FAQ's description of limited accounts. Neither names the error.
3. **Frozen accounts.** Only the config keys are documented. No guide page exists, and the triggers are unknown. `FROZEN_METHOD_INVALID` shows up on `channels.joinChannel`.
4. **Layer 230 against the docs (225).** Not documented on the site: `wallet.*`, guard-bot joins (`chatInviteJoinResultWebView`, `messages.requestChatJoinWebView`, `toggleJoinRequest guard_bot`), `account.confirmBotConnection`, and the new `ButtonType` / `InlineButtonType` shape. Their behaviour is inferred from the schema.
5. **Which admin right each method needs.** Core docs give flags and `CHAT_ADMIN_REQUIRED` / `RIGHT_FORBIDDEN`, not a mapping. The mapping in §1 is inference, partly backed by Bot API wording.
6. **Contacts and privacy.** The docs do not state outright that adding a contact puts the user inside "My Contacts" rules. They do not say whether deleting a contact removes an `add_phone_privacy_exception`. They do not say what, if anything, the imported person is told.
7. **Request-peer buttons.** Whether `sendBotRequestedPeer` for a `requestPeerTypeChat` with `bot_admin_rights` promotes the bot in that Chat server-side. Which fields (`name/username/photo_requested`) the bot then receives is inferred from `requestedPeer*`.
8. **Join requests.** No requester-side method to withdraw a pending join request was found in the layer-230 schema. It may be done by another route, for example leaving.
9. **People Nearby (`contacts.getLocated`).** The method is in the schema, but the server may no longer serve the feature.
10. **Account self-destruct.** Whether an MTProto session like tg-mcp's counts as "coming online" for `AccountDaysTTL` is undocumented.
11. **Rejoin effects.** What a member who left and rejoined can see of the history (with pre-history hidden) is not covered by the pages fetched.
12. **Undo of `bots.allowSendMessage`.** No documented revoke was found.
