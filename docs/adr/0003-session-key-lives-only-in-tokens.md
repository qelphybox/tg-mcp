# The Session key lives only in Tokens

A database dump must not give access to any Telegram session, yet a server restart must not force re-login. So each Grant has a random Session key that encrypts its Telegram session (XChaCha20-Poly1305), and the key itself is never stored: every Token we issue is `<token id>.<256-bit secret>`, and per Token we store only a verifier and a Wrapped key, both derived from the secret with HKDF-SHA256. A request (or a refresh) presents a Token, we verify it, unwrap the Session key and decrypt the Telegram session in memory. The server is its own OAuth 2.1 authorization server because no external IdP could carry this key material.

## Consequences

- Refresh rotates Tokens; each new Token gets its own Wrapped key. The old refresh Token is marked consumed and stays fully usable for a 60-second grace window from its first use (so two client processes refreshing at once, or a retry after a lost response, both work; each gets its own pair). The window is enforced when a Token is verified; a sweep every minute then deletes the Wrapped key from the database file (SQLite `secure_delete`), and only its id, Grant, verifier and original expiry remain until that expiry. A consumed Token never keeps a Grant alive.
- Presenting a consumed refresh Token after its grace window, or any genuine refresh Token from a client the Grant wasn't issued to, is treated as theft and revokes the whole Grant (Grant, Telegram session, every Token). Only a matching secret does this: a forged one is just invalid. The client gets the usual `invalid_grant`; the log says `refresh_reuse` or `foreign_client` with the Grant id. The Telegram session is logged out only if a Live client still holds it in memory; otherwise it stays a dead entry in Active sessions, since no one holds its auth key any more.
- The authorization code is short-lived and held in memory only (with the Session key); a restart mid-login means logging in again.
- Revoking a Grant (and calling `auth.logOut`) needs a live Token, since only a Token can decrypt the Telegram session. The one exception is revocation for theft (above), which uses a pooled Live client's session if there is one, and otherwise cannot log out.
- Losing every Token of a Grant makes its Telegram session unrecoverable by design; the user logs in again.
- A Grant with the `send` Scope also keeps its Send allow-list (ADR-0005) as one blob sealed with the Session key: the same XChaCha20-Poly1305, its own AAD `tg-mcp/send-allow-list/v1:` + Grant id, so it never opens as the Telegram session or as another Grant's list, and a database writer can't widen it. The plaintext (version, flags, Chat ids) is padded to a multiple of 512 bytes, so the ciphertext's length tells the list's size only roughly. Like the session, it opens only with a Token, and changing it means a new Grant. (Until 0.3.0 the blob also held the Auto-send choice and the Confirmation cookie's verifier; lists sealed then still open, and both are ignored: ADR-0008.)
- `/forget` (#63) deletes every Grant of an Account without a Token, after a fresh QR login proves the user owns it: deleting destroys, never decrypts, so it needs no Session key. A Grant's Telegram session is logged out only where the Client pool still holds its Live client; the rest stay in the Account's Active sessions, unusable by anyone, for the user to end there. The session made for the check is logged out at once.
- A Media link is downloaded without a Token (an agent's shell has none). Like the authorization code, it is issued from a Token-authenticated call and keeps what the download needs (a reference to the Grant's Live client) in memory only, for a few minutes and a few downloads; a restart kills it. Nothing about it is persisted.
